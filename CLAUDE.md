# CRM-AUTO — КРАТКОЕ РУКОВОДСТВО ДЛЯ CLAUDE

## 1. Что это за проект

CRM-AUTO — локальная Windows CRM для менеджера отдела автомобилей под заказ.

Приложение работает локально на одном ноутбуке. Основная задача — вести клиентов, автомобили, документы, статусы и дальнейший процесс сделки без огромных Excel-таблиц и дублирования данных.

Целевой экран: **14 дюймов / 1366×768**. Интерфейс должен быть компактным, карточным и удобным для ежедневной работы.

---

## 2. Главное правило работы

Перед изменениями **не изучай весь проект подряд**.

Сначала:

1. Прочитай этот файл `CLAUDE.md`.
2. Прочитай текущую задачу пользователя.
3. Найди только файлы, относящиеся к этой задаче.
4. Изучи импорты и зависимости этих файлов.
5. Внеси минимально необходимые изменения.

Не переписывай работающие части проекта без необходимости.

Не создавай новый проект и не меняй архитектуру без согласования.

---

## 3. Архитектура

Стек:

* Electron
* React
* TypeScript
* Vite
* SQLite
* better-sqlite3
* IPC между React и Electron

Принцип:

**React UI → ipcService → preload/contextBridge → Electron IPC → SQLite**

React renderer не должен напрямую обращаться к SQLite или Node.js.

---

## 4. Основная структура проекта

```text
electron/
  main.ts                 # Electron main process
  preload.ts              # Безопасный IPC bridge
  ipc/
    database.ts           # Работа с SQLite
    files.ts              # Работа с файлами клиентов
    documents.ts          # Документы
    backup.ts             # Резервные копии
    messaging.ts          # Открытие мессенджеров

src/
  pages/                  # Основные экраны
  components/             # UI-компоненты
  hooks/                  # React hooks
  services/ipcService.ts  # Единая точка IPC для React
  types/                  # TypeScript types
  utils/                  # Форматирование и вспомогательные функции
  database/               # Схема/миграции при необходимости

templates/                # Будущие шаблоны договоров DOCX
car_brands.txt            # Исходный текстовый справочник марок
```

Перед изменением файла сначала проверь его реальное содержимое и существующие импорты. Структура могла измениться после предыдущих сессий.

## 5. Важная бизнес-логика

### Клиент

Клиента можно создать сразу после первого звонка.

Не нужно ждать согласия на обработку персональных данных для создания карточки.

### Согласие на обработку ПД

Это отдельный документ клиента.

Статусы:

* Не запрашивалось
* Отправлено клиенту
* Получено
* Проверено

При статусе «Получено» фиксируется дата получения.

Все изменения должны реально сохраняться в SQLite и фиксироваться в истории клиента.

### Автомобиль / заказ

Один клиент может иметь несколько заказов.

**Номер договора (`contract_number`) принадлежит заказу (`orders`), а не клиенту (`clients`).**

Марка автомобиля выбирается из справочника `car_brands`.

Модель пока вводится текстом.

### Поиск

Единый поиск должен находить клиента по:

* ФИО;
* телефону;
* email;
* номеру договора;
* марке и модели автомобиля;
* контактам/мессенджерам.

---

## 6. Удаление и корзина

Клиенты не должны физически удаляться сразу.

Обычное удаление:

**Удалить → подтверждение → переместить в Корзину**

Из корзины:

* восстановить;
* удалить окончательно с отдельным последним предупреждением.

Нельзя делать опасное удаление одним случайным кликом.

Для файлов используется отдельное подтверждение окончательного удаления.

---

## 7. Документы и персональные данные

CRM работает локально.

Не отправляй данные клиентов в сторонние сервисы.

Документы клиентов в будущем включают:

* согласие на обработку ПД;
* паспорт;
* СНИЛС;
* ИНН;
* договор;
* подтверждение оплаты;
* доверенность;
* прочее.

Файлы должны храниться локально, а база данных хранит информацию и пути к ним.

Не используй mock data для функций, которые должны работать с реальными данными.

---

## 8. Расширяемость

В проекте предусмотрены:

* `custom_fields`
* `custom_field_values`

Архитектура должна позволять добавлять новые поля в будущем без переделки всей базы.

Не удаляй эту возможность при локальных исправлениях.

---

## 9. UI

Пользователь не программист.

Интерфейс должен быть простым и понятным.

Не использовать:

* огромные таблицы;
* сложные технические настройки в основных экранах;
* `prompt()` браузера для важных действий.

Предпочтительно:

* карточки;
* вкладки;
* компактные формы;
* выпадающие списки;
* нормальные модальные окна.

---

## 10. Обязательное правило: никаких фальшивых функций

Если кнопка существует, она должна работать.

Не считать задачу выполненной, если:

* UI меняется визуально, но SQLite не сохраняет данные;
* данные исчезают после перезапуска;
* IPC handler отсутствует;
* функция является заглушкой.

Для функций сохранения всегда проверять полный путь:

**UI → React state → IPC → SQLite → повторное чтение → UI**

---

## 11. Перед завершением задачи

Проверь только то, что относится к текущей задаче.

Минимум:

1. TypeScript не имеет сломанных импортов.
2. Изменённая функция реально работает.
3. Данные сохраняются после перезапуска приложения.
4. Выполнить `npm run build`, если изменения затрагивают сборку.
5. Не удалять работающий функционал ради упрощения.

---

## 12. GitHub

Работа ведётся через существующий GitHub-репозиторий.

Не создавать новый репозиторий.

Не удалять историю Git.

После успешного выполнения задачи:

1. Сделать commit с понятным сообщением.
2. Сделать push в текущую рабочую ветку, если пользователь попросил сохранить изменения на GitHub.
3. В отчёте указать commit hash.

Пользователь получает изменения локально через `git pull`.
