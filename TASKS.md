# CRM-AUTO — TASKS

## 1. О проекте

Локальная CRM для менеджера отдела автомобилей под заказ.

Приложение работает локально на Windows. Данные клиентов и документы не должны уходить в интернет без явного действия пользователя.

Основная задача CRM — заменить ручную Excel-таблицу и уменьшить количество ручной работы менеджера при ведении клиента от первого звонка до выдачи автомобиля.

## 2. Технологии

* Electron
* React
* TypeScript
* Vite
* SQLite
* better-sqlite3
* IPC между Electron main и React renderer
* Windows

Не превращать проект в один огромный файл.

UI → hooks/services → IPC → SQLite / файловая система

## 4. Контакты

Поддерживаются:

* телефон
* Telegram
* MAX
* WhatsApp
* другие контакты

Прямые сообщения от имени пользователя через API не используются.

Для мессенджеров используется логика:

1. CRM готовит сообщение.
2. Копирует его в буфер обмена.
3. Открывает соответствующий чат.
4. Менеджер вставляет сообщение и отправляет его сам.

## 6. Важный рабочий сценарий документов

Клиент может прислать документы постепенно:

* сначала согласие;
* потом паспорт;
* потом СНИЛС;
* потом ИНН;
* потом договор;
* потом чек.

Но клиент также может прислать ВСЕ документы сразу.

CRM должна поддерживать оба сценария.

Например:

`паспорт.pdf`
`snils.pdf`
`inn.pdf`
`soglasie.pdf`
`dogovor.pdf`

выбираются одновременно и распределяются по соответствующим типам.

## 7. Автосохранение

Для обычных изменений не требовать постоянного нажатия кнопки OK.

Изменения должны сохраняться автоматически.

Например:

* статус документа;
* комментарий;
* добавление документа;
* добавление файла;
* изменение срока;
* изменение статуса заказа.

После сохранения допустим короткий индикатор:

`✓ Сохранено`

Не использовать `prompt()` для обычных действий.

## 10. Срок доставки

Стандартный срок доставки сейчас:

**2 недели.**

Но это только значение по умолчанию.

Менеджер должен иметь возможность указать собственный срок.

Например:

* 14 дней
* 21 день
* 75 дней
* 2 месяца
* любой другой срок

После даты оплаты CRM рассчитывает ориентировочную дату прибытия.

Должна также быть возможность вручную изменить конечную дату прибытия.

В карточке заказа показывать:

* дату оплаты;
* установленный срок;
* ориентировочную дату прибытия;
* количество оставшихся дней;
* просрочен ли срок.

## 11. Следующие этапы после оплаты

После оплаты автомобиль проходит:

Оплачен
→ Ожидание доставки
→ Таможня
→ Брокер
→ Доверенность
→ Таможенное оформление
→ В пути по РФ
→ Прибыл в офис
→ Осмотр
→ Клиент приглашён
→ Выдан

Статусы должны быть понятными пользователю и по возможности редактируемыми через настройки.

CRM локальная.

Не отправлять данные клиентов в облако автоматически.

Особенно:

* паспорт;
* СНИЛС;
* ИНН;
* договоры;
* платежные документы.

Не добавлять внешние API без необходимости и без явного согласия пользователя.

## 21. Правила для AI-разработчика

Перед изменением кода:

1. Прочитай этот `TASKS.md`.
2. Определи, какие существующие файлы относятся к задаче.
3. Не изучай весь проект без необходимости.
4. Не переписывай рабочие модули целиком.
5. Не меняй архитектуру без необходимости.
6. Не удаляй работающий функционал.
7. Не создавай монолитные файлы.
8. Сохраняй модульную архитектуру.
9. После изменений обязательно запусти:
   `npm run build`
10. Если build не проходит — исправь ошибки до завершения задачи.
11. Не утверждай, что функция работает, если она не была проверена.
12. Если для проверки нужен реальный Windows GUI, явно сообщи об этом.
13. После завершения кратко сообщи:

* что изменено;
* какие файлы изменены;
* что проверено;
* остались ли проблемы.

## 23. Главное правило

CRM создаётся прежде всего для реальной ежедневной работы менеджера.

Приоритет:

**простота → скорость → отсутствие забытых клиентов/задач → автоматизация → удобство.**

Не усложнять интерфейс функциями, которые менеджеру не нужны каждый день.
