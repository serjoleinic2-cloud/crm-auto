# PROJECT.md — CRM-AUTO

## 1. Что это за проект

**CRM-AUTO** — локальная Windows CRM для менеджера отдела автомобилей под заказ.

Цель программы — заменить личные Excel-таблицы и ручное дублирование информации. CRM должна помогать вести клиента от первого звонка до получения автомобиля.

Приложение рассчитано на работу одного менеджера на личном Windows-ноутбуке.

Основной принцип: **данные хранятся локально и не должны самостоятельно отправляться в интернет**.

---

# 2. Главная бизнес-задача

Типичный процесс работы менеджера:

1. Клиент звонит или пишет.
2. Менеджер фиксирует контактные данные и интересующий автомобиль.
3. Клиенту отправляется согласие на обработку персональных данных.
4. После получения подписанного согласия собираются необходимые документы.
5. Менеджер готовит Word-договор, печатает договор и согласие либо использует оригиналы, подписанные в офисе; комплект передаётся в папку бухгалтерии.
6. Клиент подписывает договор.
7. Ожидается и фиксируется оплата автомобиля; агентские учитываются отдельно.
8. После оплаты автомобиль находится в пути.
9. После прибытия менеджер назначает плановую дату выдачи.
10. CRM создаёт задачу проверить автомобиль за два дня до выдачи.
11. После проверки менеджер приглашает клиента и фиксирует выдачу.

CRM должна постепенно автоматизировать этот процесс.

---

# 3. Основные принципы

* CRM работает локально на Windows.
* Основные данные хранятся в SQLite.
* Никаких облачных баз данных.
* Интерфейс рассчитан на **14-дюймовый экран / 1366×768**.
* Не превращать CRM в большую Excel-таблицу.
* Использовать карточки, вкладки, компактные формы и модальные окна.
* Не создавать фальшивые функции и заглушки.
* Если функция отображается в интерфейсе, она должна реально работать.
* Не переписывать работающие части проекта без необходимости.
* Изменять только то, что относится к текущей задаче.

# 4. Технологии и архитектура

Стек проекта:

* Electron
* React
* TypeScript
* Vite
* SQLite
* better-sqlite3

Архитектурное правило:

```text
React UI
   ↓
Hooks / Services
   ↓
ipcService
   ↓
Electron preload / contextBridge
   ↓
Electron IPC handlers
   ↓
SQLite
```

React renderer **не должен напрямую обращаться к SQLite, Node.js или файловой системе**.

Все операции должны проходить через безопасный IPC.

# 6. Клиенты и заказы

## Клиент

Клиента можно создать сразу после первого звонка или обращения.

Не нужно ждать получения согласия на обработку персональных данных для создания карточки клиента.

Основные данные:

* ФИО;
* телефон;
* email;
* мессенджеры;
* комментарии;
* статус;
* история действий.

## Заказ

Один клиент может иметь несколько заказов.

**ВАЖНО: `contract_number` принадлежит заказу (`orders`), а не клиенту (`clients`).**

Данные заказа могут включать:

* марку;
* модель;
* год;
* комплектацию;
* описание;
* цену;
* комментарий;

## 6.1. Папка заказа, бухгалтерия и общие таблицы

У каждого заказа есть отдельная папка. В ней обязателен комплект из шести документов:

1. скан паспорта с пропиской;
2. ИНН из Госуслуг или скан оригинала;
3. СНИЛС из Госуслуг или скан оригинала;
4. согласие на обработку ПД — распечатка или оригинал, подписанный в офисе;
5. Word-договор, заполненный при первом оформлении;
6. скан подписанного обеими сторонами договора или скан оригинала.

После получения полного комплекта менеджер печатает договор и согласие (либо использует оригиналы, подписанные в офисе), кладёт их в папку для бухгалтерии и отмечает это в CRM.

CRM должна помогать подготовить отдельные записи для вкладок «Договор», «Оплата» и отдельной таблицы агентских. Каждая запись подтверждается отдельно, с датой и суммой, чтобы этапы нельзя было случайно забыть или продублировать.
* дату оплаты;
* сроки доставки.

# 7. Согласие на обработку персональных данных

Согласие на обработку персональных данных — отдельная сущность/документ клиента.

При создании клиента автоматически создаётся запись согласия.

Статусы:

* Не запрашивалось;
* Отправлено клиенту;
* Получено;
* Проверено.

При выборе статуса **«Получено»** автоматически фиксируется дата получения.

Можно добавить:

* путь/имя скана;
* примечание.

Все изменения должны:

1. реально сохраняться в SQLite;
2. сохраняться после перезапуска;
3. фиксироваться в истории клиента.

Получение согласия не должно блокировать создание клиента.

# 9. Quick Add — быстрое создание клиента

Форма должна быть удобной для ежедневной работы.

Не заставлять менеджера вручную писать марку автомобиля каждый раз.

Марка выбирается из выпадающего списка `car_brands`.

Модель вводится текстом.

Форма разделена на компактные блоки:

* Клиент;
* Автомобиль;
* Задача.

Не превращать форму в огромную длинную таблицу.

---

# 10. Корзина и удаление

Клиент не должен физически удаляться одним нажатием.

Обычное удаление:

```text
Удалить → подтверждение → Корзина
```

Используется soft delete.

В корзине должно быть:

* восстановление клиента;
* окончательное удаление.

Окончательное удаление всегда требует отдельного последнего подтверждения.

При удалении клиента необходимо учитывать связанные данные и документы.

---

# 11. Документы и файлы

В будущем CRM будет работать с документами:

* согласие на обработку ПД;
* паспорт;
* СНИЛС;
* ИНН;
* договор;
* подтверждение оплаты;
* доверенность;
* прочее.

Файлы должны храниться локально.

База данных хранит информацию о документах и пути к файлам.

Важно различать:

* **отвязать файл от карточки** — удалить связь в CRM;
* **удалить файл физически** — удалить файл с диска.

Для реальных документов клиента физическое удаление должно требовать подтверждения.

Удаление файлов должно поддерживать выбор через чекбоксы и последнее предупреждение перед окончательным удалением.

# 12. История клиента

Все важные действия должны автоматически фиксироваться в истории:

* добавление или удаление заказа;
* работа с документами;
* важные изменения данных.

История является журналом действий и не должна быть просто декоративным элементом.

# 15. Безопасность и персональные данные

CRM содержит чувствительные персональные данные.

Правила:

* не отправлять данные клиентов во внешние сервисы без явного действия пользователя;
* не использовать облачную БД;
* не использовать реальные данные клиентов для тестирования;
* при тестировании использовать вымышленных клиентов.

PIN-вход в CRM **не используется**, так как приложение работает локально, а доступ к компьютеру защищается средствами Windows.

1. Прочитать `PROJECT.md`.

Не нужно читать весь проект подряд, если задача локальная.

Не создавать новый проект.

Не менять стек без необходимости.

Не заменять работающий код заглушками.

# 19. Проверка изменений

После выполнения задачи проверять полный путь работы функции:

```text
UI → React → IPC → SQLite/Filesystem → повторное чтение → UI
```

Изменение считается выполненным только если:

* функция реально работает;
* данные сохраняются;
* данные не исчезают после перезапуска;
* нет сломанных импортов и TypeScript-ошибок.

Если задача затрагивает сборку — выполнить:

```powershell
npm run build
```

При возможности также проверить:

```powershell
npm run dev
```

Существующий GitHub-репозиторий является основным местом обмена кодом между разными сессиями и инструментами.

Не создавать новый репозиторий.

Не удалять Git-историю.

Рабочая схема:

```text
ИИ вносит изменения
        ↓
GitHub
        ↓
Пользователь выполняет git pull
        ↓
D:\crm-auto
        ↓
npm run dev
```

После успешной работы и по необходимости сохранения изменений:

* сделать понятный commit;
* сделать push в рабочую ветку;
* сообщить commit hash.
